## Athy Labs: automated hydroponics and a code generator

From 2019 to 2023 most of my side-project time went into something I called **Athy**, short for *Automated Hydroponics*. It started as a way to monitor a hydroponics setup with cheap sensors and turned into a small platform, and then into a code generator. The code lives in the [athy-org](https://github.com/athy-org) GitHub org. This post is the map of what is in there.

### The hydroponics platform

The idea was a pipeline from a sensor in the grow tray to data in a database I could query and act on.

- **Sensors (`athy-micro-device`).** ESP32 DevKit boards reading the environment. I first wrote the firmware with the Arduino IDE, then moved to C# on [.NET nanoFramework](https://www.nanoframework.net/), which let me use the same language on the board as everywhere else. My [notes on nanoFramework and the ESP32](/iot/microcontrollers/esp32/2021/06/19/nanoframework-and-esp32.html) came out of this.
- **Collector (`athy-collection-device`).** A .NET service running in Docker on a Raspberry Pi 3B+ (later a Pi 4) that gathered readings from the sensors and forwarded them.
- **Gateway (`athy-gateway-api`).** A .NET API backed by PostgreSQL that received the device data. It was a monolith on purpose, with a note in the README that it would "likely" be split into microservices later.
- **Background jobs (`athy-hosted-service`).** A hosted service on a DigitalOcean droplet running scheduled jobs such as database clean-up.
- **Shared library (`athy-component`).** Common API responses, exception-to-HTTP-status mapping and data-access helpers, published as a NuGet package with versioning handled in CI.
- **Infrastructure (`athy-infra`).** Terraform, run from a Docker image, with secrets in HashiCorp Vault.

There was also Jenkins, SonarQube, Trivy scans and architecture diagrams in `athy-project-docs`. Looking back, that is a lot of enterprise scaffolding for a few plants. It was also the point: I wanted somewhere to practise the whole stack, not just the interesting bits.

### The code generator

Every new service in the platform started with the same boilerplate: solution layout, API project, error handling, Docker files, CI. So I started automating that, and the automation became its own project.

- **`athy-templates`** holds `dotnet new` templates for a Web API solution, with parameters for things like the client and project codes and ports.
- **`athy-generator`** reads an OpenAPI spec and generates a working .NET Web API solution from those templates. It runs as a console app or a `dotnet` global tool, and there was an API version that ran in Azure with queue-based jobs and Azure Storage.
- **`athy-static-web`** is the landing page for it. It used to live at `generator.athylabs.co.za` and is back up as an archived showcase at [athy-generator.lillylabs.co.za](https://athy-generator.lillylabs.co.za).

Before building it I compared the existing options. That write-up is [Comparison of code-generation tools](/development/microservices/code-generation/2022/01/10/code-generator-comparison.html). The short version is that `dotnet new` templates can't generate one controller method per endpoint by themselves. The generator therefore rewrites the template from the spec first, then runs it.

### Where it is now

The athylabs domains have lapsed and the projects are dormant. The repos are kept as a record, and the tech is dated: .NET versions from that era, Jenkins and Terraform 0.12. Some of it may come back. A hydroponics rig with today's tooling would be a fun rebuild.

My current work is at [Lilly Labs](https://lillylabs.co.za).
